# Backend Observability — Design

Status: draft for review (2026-10-17). Scope: `backend/` (Forge) only.

## Intent

Forge exists to speed up scaffolding work that repeats across projects. Every new service needs the same logging, correlation, metrics and runbook groundwork. Today a generated project has a basic `CorrelationIdFilter`, the actuator starter and a text log pattern, and nothing else.

The goal is that a project generated by `forge new` meets the baseline of the **Cross-Project Observability, Logging, and Monitoring Standard** (`knowledge-base/cross-project-observability-standard.md`, v1.0) from day one, so the logging and monitoring setup does not have to be re-done by hand per project.

Decisions fixed by the user:
- The standard is the source of truth. The MeowGo server (`meowgo_server_java`) already implements Phase 1 and is a **reference to generalize from**, not a target and not a spec. Where the two differ, the standard wins.
- Scope is **Phase 1 (logging foundation) and Phase 3 (metrics, dashboards, alerts, runbook)**. Phase 2 (central collection pipeline, access control) is only partly addressed (see Non-goals). Phase 4 (OpenTelemetry tracing, SLOs) is out.
- Observability is part of `base-layered`, not an opt-in feature. For `minimal`: logging foundation yes, metrics and monitoring stack no.
- The development machine has **no Docker**. Everything Forge verifies locally must work without Docker; anything that needs Docker is verified in the generated project's CI.
- No new CLI flags and no new wizard prompts.

## Template split

| Part | `base-layered` | `minimal` |
|---|---|---|
| Phase 1: structured logs, request log, correlation, job context, redaction, logging doc | yes | yes |
| Phase 3: Micrometer/Prometheus metrics, management port, health probes | yes | no |
| `observability/` stack files, `docker-compose.observability.yml`, runbook, CI config check | yes | no |

A new `ForgeConfig` property `include_monitoring` (`self.template != "minimal"`) is exposed through `template_context()`, following the `use_liquibase` pattern. It gates the content that must differ inside shared files (`pom.xml`, `application.yml`, `ci.yml`). Files that exist only for monitoring are removed from `minimal` through its `manifest.py` `EXCLUDES`:

```
observability/*
docker-compose.observability.yml
docs/observability/runbook.md
```

## Phase 1 — logging foundation (both templates)

Uses Spring Boot's built-in structured logging with the ECS format. No new logging dependency.

**Output.**
- `prod` profile: `logging.structured.format.console=ecs`, one JSON object per line on stdout, timestamps in UTC, stack traces bounded (4096 characters, as MeowGo does; exact property names are taken from MeowGo's `application-prod.yml` and verified against the Boot version in the template's `pom.xml`).
- `dev` profile: readable text pattern including `request_id`.
- Containers write to stdout; there is no file logging, so no rotation settings are needed (OBS-06). The logging doc states this explicitly.

**Service identity (OBS-02).**
- `service.name` = `spring.application.name` (already `{{ artifact_id }}`).
- `service.version` = the project version via Maven resource filtering (`@project.version@`).
- `deployment.environment.name` = `${DEPLOYMENT_ENVIRONMENT:production}` in `prod`, `development` in `dev`.

**Components** (package `common/config`):

| Class | Responsibility |
|---|---|
| `CorrelationIdFilter` (rewritten) | MDC key becomes `request_id` (the standard's name; the template used `correlationId`). An inbound `X-Correlation-ID` is reused only if it matches `[A-Za-z0-9._-]{1,64}`; anything else is replaced by a UUID. Removes only its own MDC key instead of `MDC.clear()`. The id is echoed on the response header. |
| `RequestLogFilter` (new) | One `http.request.completed` event per request with `http.request.method`, `http.route` (matched route template, or `UNMATCHED`, never the raw path), `http.response.status_code` and `duration_ms`. It never reads query strings, headers, cookies or bodies. Level: ERROR for 5xx or an escaped exception, WARN at or above `app.logging.slow-request-ms` (default 2000), DEBUG for the health probe, INFO otherwise. Ordered just inside `CorrelationIdFilter`. |
| `JobContext` (new) | `JobContext.run(jobName, task)` puts `job` and a fresh per-run `request_id` into MDC for scheduled work and removes both afterwards. The template has no scheduled jobs yet; the helper ships so projects that add them follow the same convention. |
| `SensitiveDataCustomizer` (new) | Structured-logging members customizer that masks values for keys matching a denylist (`password`, `secret`, `token`, `authorization`, `cookie`, `api[_-]?key`, ...) in MDC and key-value pairs before the line is emitted (OBS-04, standard 11.2). It complements, and does not replace, the rule of never passing sensitive data to a logger. |

`GlobalExceptionHandler` is reviewed so that each failure is logged once, with a stable event name and no request or personal data in the message (standard 7.5, anti-pattern "log at every layer"). Stable event names follow `domain.entity.action[.outcome]`.

**Docs.** `docs/observability/logging.md` (both templates) records: the field schema and the ECS-to-standard name mapping, severity policy, event naming, the rules for writing new log lines (no query strings, bodies or personal data; no IDs in event names), the stdout-only decision, and the retention statement (see Retention).

### Field mapping (ECS output to the standard's conceptual fields)

| Standard field | Emitted as |
|---|---|
| `timestamp` | `@timestamp` (UTC) |
| `severity` | `log.level` |
| `message` | `message` |
| `event.name` | `event.name` |
| `service.name` / `service.version` | `service.name` / `service.version` |
| `deployment.environment.name` | `service.environment` |
| `request_id` | `request_id` (MDC) |
| `http.request.method`, `http.route`, `http.response.status_code`, `duration_ms` | same names (key-values) |
| `error.type`, `exception.stacktrace` | `error.type`, `error.stack_trace` |

The standard allows platform-native schemas as long as the mapping is documented; this table is that documentation and is copied into `logging.md`.

## Phase 3 — metrics and monitoring (`base-layered` only)

**App side.**
- `io.micrometer:micrometer-registry-prometheus` added to `pom.xml` under `{% if include_monitoring %}`.
- Actuator exposure: `health,info,prometheus`; liveness and readiness probes enabled.
- `management.server.port` = `8081` (configurable through `MANAGEMENT_SERVER_PORT`). Business traffic stays on 8080 and the metrics endpoint is not served there, which is the generated project's access control for the metrics endpoint (standard 19: "metrics endpoints exposed publicly"). The template has no Spring Security, so the port split is the control; the runbook states that production must not publish 8081 beyond the monitoring network.
- Common tags: `application`, `environment`. HTTP server metrics use route templates (Spring's default `uri` tag), with histogram buckets enabled for `http.server.requests` (Prometheus histograms aggregate across instances, standard 9.2).
- Metric groups delivered by default instrumentation: traffic, errors, latency (HTTP); saturation (JVM memory, GC, threads, HikariCP pool); dependency health (HikariCP and DB health indicator); runtime (JVM). No custom per-entity metrics.

**Stack files** (rendered into the project, `base-layered` only):

```
docker-compose.observability.yml      # overlay: Prometheus, Grafana, Loki, Alloy
observability/prometheus/prometheus.yml
observability/prometheus/alerts.yml
observability/grafana/provisioning/datasources/datasources.yml
observability/grafana/provisioning/dashboards/dashboards.yml
observability/grafana/dashboards/service-overview.json
observability/loki/loki-config.yml
observability/alloy/config.alloy
docs/observability/runbook.md
```

- **Prometheus** scrapes `host.docker.internal:8081/actuator/prometheus` for local runs; the job is labelled with the service name. Retention is bounded (`--storage.tsdb.retention.time`).
- **Alerts** (`alerts.yml`) carry `severity` and `team` labels and `summary`, `impact`, `first_checks` and `runbook` annotations (standard 14.2): service down, 5xx ratio, p95 latency, JVM heap saturation, Hikari pool saturation. Thresholds are starting points and are labelled as such in the runbook; low-traffic services are called out as needing absolute counts or longer windows.
- **Grafana** is provisioned with one dashboard: traffic, error ratio, latency percentiles, saturation, dependency health.
- **Loki + Alloy** collect container stdout. Labels stay low-cardinality (service, environment); `request_id` stays in the log body (standard 13). Local note: Alloy reads container logs, and a locally run `mvn spring-boot:run` is not a container, so locally this stack shows metrics immediately and logs only once the app runs in a container. The Dockerfile that makes this seamless belongs to roadmap item 2 (features and DevOps files) and is not added here.
- **Runbook** (`docs/observability/runbook.md`, OBS-10): where logs, metrics and alerts are; how to filter by `request_id`; investigation steps for error, latency and saturation; telling an application failure from a telemetry failure; ownership and escalation placeholders; handling of discovered secrets.

## Retention (OBS-06, standard 13)

The docs state, per telemetry class, the defaults shipped in the local stack (Prometheus 15 days, Loki 7 days) and that production retention is a decision for the owning team, with a table the team fills in. Forge does not invent organization policy.

## Forge-side changes

1. `core/config_schema.py`: `include_monitoring` property, added to `template_context()`.
2. `templates/minimal/manifest.py`: add the three `EXCLUDES` globs above.
3. `cli.py`: add the new always-present files to `EXPECTED_STRUCTURAL_PATHS` / `expected_structural_paths()` (filtered by `EXCLUDES` as today).
4. `core/validator.py`: new `check_observability(target_dir, include_monitoring)`, Docker-free:
   - the listed files exist (structure check, extended);
   - `alerts.yml`, `prometheus.yml`, `loki-config.yml`, Grafana provisioning YAML and the dashboard JSON parse (PyYAML is added as a backend dependency; Alloy syntax is checked for existence only);
   - **metric consistency**: every metric name referenced in alert expressions and dashboard queries is in a registry of metrics the app is known to expose (a small curated list in the validator module, covering `up`, `http_server_requests_seconds_*`, `jvm_*`, `hikaricp_*`, `process_*`). The token scan is best-effort and is documented as such. This keeps dashboards and alerts from drifting from what the app emits.
5. `cli.py` pipeline runs `check_observability` after the structural check and before the compile check, with the same delete-on-failure prompt.
6. `README.md` template and `QUICK_REFERENCE`/`CHANGELOG` of `backend/` describe the new behavior.

## Generated-project CI

`ci.yml` gains, under `{% if include_monitoring %}`, an `observability-config` job that runs real validators in Docker on the CI runner: `promtool check config` and `promtool check rules` (via the `prom/prometheus` image) and `docker compose -f docker-compose.yml -f docker-compose.observability.yml config -q`. It uses `docker run` directly, so it adds no third-party GitHub Action (the existing workflow pins actions by SHA and runs zizmor).

## Testing

**Docker-free, local and in Forge's own suite:**
- Unit tests of `check_observability` (valid tree passes; unknown metric, malformed YAML, missing file each fail with a clear message) and of `include_monitoring` / manifest exclusions for both templates.
- `tests/test_generation.py` renders both templates and:
  - confirms `minimal` contains no `observability/` files and no `micrometer-registry-prometheus`, while its logging files are present;
  - runs `check_observability` on `base-layered`;
  - runs `mvn test` restricted to the logging test classes (no database), in addition to the current `test-compile`.

**Generated unit tests (plain JUnit, no database, no Docker), included in both templates:**
- `CorrelationIdFilterTest`: valid id reused; CR/LF, over-length and illegal characters replaced; only own MDC key removed.
- `RequestLogFilterTest`: route template not raw path; `UNMATCHED` for no handler; no query string, header or body in the event; level mapping (5xx, slow, health).
- `JobContextTest`: MDC set during the run and removed after, including on exception.
- `SensitiveDataCustomizerTest`: denylisted keys are masked; a known test secret does not appear in the formatted line.
- A log-format test that formats an event with the ECS formatter and asserts it parses as JSON with the required fields, and that an injected `\n{"fake":true}` value stays inside one JSON line (OBS-01, standard 17). The plan verifies the lightest way to do this without starting the full application context; if that proves impractical, it falls back to `ApplicationContextRunner`.

New classes must satisfy the template's existing 90% JaCoCo line-coverage gate.

## Standard coverage

| ID | Met by |
|---|---|
| OBS-01, OBS-02 | ECS JSON in `prod`, service identity properties, format test |
| OBS-03 | `CorrelationIdFilter`, `JobContext` |
| OBS-04 | `SensitiveDataCustomizer`, `RequestLogFilter` field policy, tests |
| OBS-05 | Documented as the owning team's decision; local Loki stack for development. Not satisfiable by a generator. |
| OBS-06 | stdout-only logging, bounded stack traces, documented retention |
| OBS-07 | Micrometer metrics, Grafana dashboard |
| OBS-08 | `alerts.yml` with severity, owner label and response annotations |
| OBS-09 | Management port separation; access roles documented as the team's decision |
| OBS-10 | `runbook.md` (`base-layered`) and the investigation section of `logging.md` (`minimal`) |

## Non-goals

- Tracing, OpenTelemetry SDK or Collector, W3C `traceparent` propagation, SLO and error-budget alerts (Phase 4).
- Choosing or provisioning a production log/metrics backend, access control for it, and audit-event handling.
- A Dockerfile or production deployment files (roadmap item 2).
- Adding observability to existing projects (`forge add`), and changing MeowGo.
- Anything for `frontend/` (Forge Web); a matching frontend design would be a separate spec.
- Verifying that Prometheus, Grafana, Loki or Alloy actually start with the generated files on the developer's machine; that is covered by CI only.

## Risks and open points for the plan

- Exact Spring Boot 4 property names for structured logging and for the stack-trace limit, and the Micrometer/Prometheus artifact coordinates, are confirmed against the version in the template's `pom.xml` and MeowGo's working configuration during planning.
- The `@project.version@` filtering in `application.yml` relies on the Spring Boot parent's resource filtering; the plan checks it still applies to the Jinja-rendered file.
- `{{ }}` inside Grafana JSON and Alloy config collides with Jinja delimiters; those files need `{% raw %}` blocks (as the frontend template does for JSX).
- Renaming the MDC key from `correlationId` to `request_id` changes the template's existing `application.yml` pattern and tests; both are updated together.
- This spec overlaps roadmap item 2 of the entity-modeling spec (`actuator/Prometheus` listed as a future feature). That item is superseded by this spec; the entity-modeling roadmap line should be updated when both are approved.
